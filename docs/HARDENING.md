# Testing and hardening

Phase 13 reviews the existing product; it does not add demo data, deploy hosting, choose a real administrator, configure Google OAuth or change financial rules. Verification results and remaining limits are recorded in [PHASE_13_HARDENING.md](PHASE_13_HARDENING.md).

## Authorization and privacy review

| Surface                                | Server boundary and regression coverage                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication                         | Password hashes use a fixed scrypt profile and constant-time comparison; registration rejects injected roles, normalizes emails and has atomic database throttles. NextAuth limits POST bodies, uses CSRF checks and same-origin redirects, and loads current role/status on protected requests. Auth unit, database and browser suites cover negative identities and session behavior. |
| Business profiles and selection        | Actor identity comes from the server session; owner IDs cannot be supplied in mutation bodies. Owned-business checks also run inside services. Selection cookies are HTTP-only and never confer ownership. Profile/delete operations use version checks and owned-row locks.                                                                                                            |
| Records, dashboards and imports        | Requests require an active owner before returning business content. Child-record lookups include business ID; database constraints bind related records to the same business. Dashboard aggregates use bound SQL parameters. Import preview signatures bind the actor, business, file, data type, reviewed values and expiry; confirmation revalidates under a lock.                    |
| Forecasts, alerts, reports and PDF     | Service calls authorize the owned business and scope children to it. Saved snapshots preserve historical amounts and classifications. PDF export loads an authorized report and local fonts; user content does not select filesystem paths.                                                                                                                                             |
| AI feedback, chat and report summaries | The provider endpoint and model are fixed, credentials remain on the server, bodies/responses and context are bounded, and external calls run outside database transactions. Completion rechecks active ownership and leases, so stale inference cannot overwrite edited content. Mock regressions cover failures, timeouts and late completion.                                        |
| Administration                         | Current active ADMIN role is checked in pages, handlers and services. Explicit select lists return registration metadata; ADMIN alone grants no access to another owner's financial records, feedback, chat or reports. Sorted actor/target locks, version checks and self-status protection serialize supported account changes.                                                       |

These are application boundaries, not protections against an operator holding database credentials. Suspension blocks subsequent protected requests; it does not cancel every already-running operation. Existing owner-isolation, forged body, stale-state, concurrency and suspension tests remain in the full regression suites.

## Input and error corrections

The XLSX preflight previously bounded a column range's `max` but not its `min`. ExcelJS's column loader also allocates the gap up to `min`; an inverted range with a very large minimum could therefore allocate excessive columns despite a small maximum. Both endpoints now must be positive integers, ordered, and within the existing 12-column limit before ExcelJS loads anything. Regression fixtures check a billion-column minimum directly against the preflight, so a future regression fails a test without allocating that range. Duplicate/out-of-range cell references, malformed XML, external links, named/merged/validation ranges, encoding, ZIP expansion, file size, row count, dates and formulas are also covered. No files are extracted to disk.

Bounded JSON/form text reading now uses strict UTF-8 decoding. Invalid or truncated bytes and interrupted streams return safe 400 responses instead of replacing bytes silently or returning an infrastructure failure. Oversized bodies still return 413. Cancellation rejections are consumed without hiding the original error. Interrupted multipart uploads likewise return a safe retry message without transport details.

Record listings, import history and template requests now reject duplicate query parameters; history/template requests also reject unsupported keys. A shared query reader preserves own keys such as `__proto__` so strict schemas can reject them. Admin and report readers no longer silently drop that key through assignment to an ordinary object's prototype setter. No query parameter can override server-side ownership.

## Accessibility and responsive review

The development-only `@axe-core/playwright` dependency is pinned at 4.13.0. Browser checks scan WCAG A/AA rules through 2.2 and axe best-practice rules across desktop, tablet and mobile. They exercise both public auth forms, the populated dashboard, records, imports, forecasting, chat, alerts, reports, business settings, administration and a record-entry dialog. Selected surfaces are checked in both themes. Violations fail the test; incomplete checks are retained in report attachments for manual review. This follows the [Playwright accessibility testing workflow](https://playwright.dev/docs/accessibility-testing).

Small primary links on the off-white background previously measured 4.46:1 contrast. The light-theme interaction color is now `#077984`; muted text uses `#596b75` so the highlighted KPI card also clears the normal-text threshold. The approved logo's brand teal is unchanged. Chart containers now use a named group role rather than placing an accessible name on an unnamed generic div. Existing tabular chart alternatives remain available. Keyboard checks cover the skip link, dialog Escape/focus restoration, navigation drawer containment and status confirmation focus. Automated checks and selected screenshot review do not establish complete WCAG conformance, screen-reader certification or arbitrary zoom/device support.

## Performance and dependency review

The isolated database suite includes a 10,000-sale synthetic fixture distributed over 365 days. It verifies exact totals, a bounded daily dashboard response, 20-row pagination at page 500, maximum-history Holt evaluation and a 1,000-row CSV parse. Measurements are written to ignored `.local/phase13-performance.json`. Functional bounds and correctness fail tests; timings are observations from one local caller, not a production SLA or concurrent load test. Existing database indexes cover business/date listings; aggregate queries run in PostgreSQL and provider calls have bounded deadlines. Catalog dropdowns and business switchers still load their owner's options; very large catalogs need separate capacity work before deployment.

The full npm audit retains four high findings in the development-only Next ESLint plugin → fast-glob → micromatch → braces chain. The [upstream advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) lists no patched version; the compatible installed braces version remains 3.0.3. A cross-major downgrade of the Next ESLint plugin was not applied. Runtime-only audit results are stated separately in the phase report. Do not interpret a production-only audit as a clean full audit.

The existing CI job runs the added tests automatically through its full unit/database/browser commands. Local verification does not prove the remote Linux job, hosted database, live Google OAuth, live NVIDIA reliability, hosting limits or production capacity. Phase 14 owns demo/deployment preparation.
